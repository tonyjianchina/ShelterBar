# 自动更新：减少重复工作，避免打断收纳栏

基线：`ffb198c811ba7b490ebd3daeef691aa18880034c`（v0.5.12 Build 36）。
独立候选分支：`codex/shelterbar-feature-polish`。

## 实际问题

`ShelterBarUpdater.performUpdate` 原来每次读取 feed 后，都会再次下载当前版本 ZIP 与
SHA256SUMS，再解压、验证签名，最后才知道“已经是最新版”。它在启动约 5 秒后和每 6
小时运行一次。即使发布资产完全没变，仍重复产生这些网络、磁盘和签名验证工作。

`ShelfViewModel.applyUpdateState` 还把后台“已是最新版”与失败结果写入 `message`。
基线 `ShelfView` 的 message 分支会替换图标区域；因此自动检查也可能突然把可操作图标
换成提示文字。

## 方案

- 始终读取 feed；仅当一次完整安装器验证返回“无需安装”后，保存已验证结果。
- 缓存关联 feed URL、已安装版本/构建号、候选版本，以及 ZIP/清单各自的下载 URL 和
  SHA256 摘要。两份真实下载内容的摘要也必须与 feed 完全相同，才能写入缓存。
- 下次后台检查命中这个结果时，只显示更新菜单状态，跳过下载、解压和签名复核。
- 同一营销版本重新发布更高 Build 会改变 ZIP 摘要，即刻使缓存失效。清单单独变化、
  更换 feed 或安装构建号变化也会重新验证。
- 缺失、格式错误或与实际载荷不一致的 digest 不启用此优化。验证失败、取消不会记为成功。
- 用户显式“检查更新”保留原来的同版本重装能力，始终走完整流程。
- 自动检查结果不再覆盖收纳栏提示；失败会在菜单显示“更新失败，点击重试”。用户主动
  检查仍得到明确完成/失败说明。

## 验证

命令：

```sh
swift test --force-resolved-versions -j 2
```

结果：174 项应用测试 + 32 项核心测试 = **206 项通过**。
日志：`/tmp/shelterbar-feature-full.log`（开发机本地）。

新增 8 个行为测试（含参数化场景），覆盖重启复用、同版本 ZIP 与清单替换、手动重装、
feed 切换、安装构建号变化、缺失/无效/不匹配摘要、失败/取消后重试，以及后台提示不打断。

受控 fixture 使用 611,877 字节 ZIP 数据，调用真实 updater 协调逻辑，注入网络与安装器
结果以避免写入用户安装目录：

| 一次检查 | 请求数 | 返回字节 | 安装器准备次数 |
| --- | ---: | ---: | ---: |
| 首次未缓存 | 3 | 612,362 | 1 |
| 重启后相同资产 | 1 | 459 | 0 |

这里的字节和次数是自动化测试实测，不是互联网下载耗时或真实桌面帧率数据。
基线源码每次都会走第一行路径；本分支在 warm 状态移除了两次请求与整次准备工作。

## 风险与推荐

缓存存于应用现有 UserDefaults 中；不会缓存下载包或跳过新资产的验证。GitHub 摘要缺失
时性能回退到原逻辑。不会改变更新 feed、签名要求、安装 helper 或回滚流程。

推荐与主线程优化、UI 候选整合：收益是后台更安静、减少无用 I/O，并且不需要增加用户设置。
这不能替代真实旧版应用从公网下载并完成 bundle 交换的端到端升级验收；分支测试没有
启动生产应用、安装、修改 TCC、改变用户菜单布局或发布到远端。
